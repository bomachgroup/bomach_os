# Company Governance

## Scope and behavior

- `/company/board` ports Flutter's Meetings, Resolutions, Investors, Associates, and Partners tabs. Tab, search, and page are shareable URL state. Each tab is independently permission-gated; only the active tab's list query is enabled.
- Meetings support list, create, edit, attendees when `employees:list` is available, and cancellation through the supported delete/cancel endpoint.
- Resolutions support list, create, edit while editable, approve through the dedicated approval endpoint, and archive through the backend's DELETE endpoint. Approved and archived resolutions are not offered for editing.
- Investor records use the Shareholder API. Creation also creates a user and employee and sends a welcome email after commit; the editor explains this before the user saves. Existing shareholders can be edited or made inactive; the screen does not call the unverified shareholder delete path.
- Associates are read-only employee records. Their actual backend employment types are `surveyor-associate`, `lawyer-associate`, `architect-associate`, and `engineer-associate`; the invalid generic `associate` filter is not used.
- Partners support list, create, edit, and confirmed deletion. Partner agreements are outside this Board slice and retain their own `partner_agreements` permissions.
- `/company/compliance` is the Compliance Register described by Flutter's `ComplianceDashboardPage`; no aggregate compliance dashboard endpoint exists. The page uses the supported paginated list and CRUD routes and does not invent summary metrics.
- Compliance type, status, and priority choices are from the backend model. The department selector uses the real department list (`id` and name), not the separate department category choices endpoint. If department browsing is unavailable, an existing record retains its saved department while editing; creating a record requires department choices.
- Compliance attachments are added with the image/PDF picker and uploaded through the shared `/others/upload-file` endpoint; users do not type document URLs. Existing saved URLs remain linked in the editor and can be removed from the draft before saving. Only HTTP(S) links are rendered as links.

## Permissions

- Board route access requires at least one list permission among `meetings:list`, `board_resolutions:list`, `shareholders:list`, `employees:list`, and `partners:list`. Sidebar visibility also checks all five resources.
- Each Board tab requires its own `list` permission. Create/update/delete/approve buttons use the matching endpoint permissions. The employee Associate view is read-only. Attendee selection is shown only with `employees:list`.
- Compliance route and list require `compliance_records:list`; create, update, and delete actions separately require `compliance_records:create`, `compliance_records:update`, and `compliance_records:delete`.
- Compliance department lookup requires `departments:list`, matching the backend department list endpoint.

## API limits retained

- No compliance summary/dashboard endpoint, choices endpoint, or compliance-specific upload endpoint is available. The shared file-upload endpoint is used for picked attachments.
- Board attendee lookup reuses the active employee list only for users with `employees:list`; the API list is capped to the requested first 100 active employees in the editor.
- The employee endpoint accepts one associate employment type at a time. The all-associate tab queries the four supported types separately and combines up to 100 records per type for local paging.
- Shareholder create has the account/email side effect described above. Shareholder delete is not exposed in this UI.
- Partner agreements are not included in the Board tab; they are a separate permissioned workflow.

## Audit Log

- `/company/audit-log` reads the existing `GET /api/v1/audit-logs/` endpoint. It uses the server-supported search, user ID, audit type, status, start date, and end date filters with limit/offset pagination (10 rows per page).
- Route and query access require `audit_logs:list`, matching the backend permission. The backend currently returns the caller's permitted audit-log scope without a separate user-detail choice endpoint; the page therefore accepts a numeric user ID instead of inventing a user directory.
- Filter values and pagination live in the URL. Invalid query values are normalized; invalid calendar dates are discarded, and a reversed date range is blocked with inline guidance. Out-of-range bookmarked pages recover to the last available page.
- The list uses the `history` freshness window (120 seconds) and revalidates stale data on entry/focus/reconnect without a generic header Refresh action or polling. Cached results stay visible during background refresh and after refresh failure; first-load failure, empty results, and permission denial have separate states.
- The desktop view uses a table and narrower layouts use a compact, divided event list. The UI displays actor, activity, type, status, IP address, and timestamp; it deliberately does not render the response's `metadata` object.

## Approval Requests

- `/company/approval-requests` reads the existing `GET /api/v1/approvals/requests` endpoint. Status and text search are URL-backed, the backend scope and default limit/offset pagination are retained, and the page uses 10 records per page.
- Route/list access requires `approval_requests:list`. Request review actions are independently gated by `approval_requests:approve` and `approval_requests:reject`; the backend remains the authority for request scope and action eligibility. The existing detail permission is not required because the list response already includes the details and decision history consumed by this page.
- The review dialog shows workflow, action type, requester, submission time, current step, request details, and saved decisions. Approve posts an empty comment; reject requires a non-empty reason and sends it as the backend `comment`.
- Successful decisions invalidate the user's Approval Requests list and Company Overview data. Approval failure leaves the review dialog open and shows an error toast. Rejection failure keeps the typed reason and displays an inline retryable error. A successful decision closes the relevant dialog and shows success feedback only after the API response.
- The list uses standard freshness (60 seconds), revalidates stale data on route entry/focus/reconnect, and does not poll or add a page-specific header refresh. Cached results remain visible during background updates and refresh failures, with an inline updating cue and a local retry only after failure. First-load loading/error, filtered empty state, and permission denial are distinct. Out-of-range bookmarked pages recover to the last available page.
- Review cards keep request identity, status, workflow, description, requester, age, and current step in a responsive hierarchy. The detail dialog scrolls independently from its fixed actions; the rejection dialog focuses its required reason, and both dialogs prevent dismissal while a decision is being recorded.
- No create-request UI is added because this screen is for review and the backend's request-creation workflows are initiated from their respective business modules.
