# HR Benefits, Performance Reviews, and Work Reports

## Scope and Flutter behavior

This slice covers the read-only HR Payroll register at `/hr/benefits` (navigation label: Payroll), employee payslip history at `/dashboard/my-pay`, `/hr/performance-review`, and the HR/Admin management queue at `/hr/work-report`. Employee submissions and personal edits stay on `/dashboard/my-reports`; the HR work-report register never creates reports on behalf of an employee or routes managers through the personal editor.

- Flutter `BenefitsPage` reads payroll records and treats payroll additions as benefit names. Its category list and staff assignment dialogs only mutate controller memory; they do not call a persistence endpoint. React therefore presents persisted payroll data as a read-only HR Payroll register and does not present local toggles as real benefit enrollment. `/dashboard/my-pay` reuses the owner-scoped payroll list API but always requests the signed-in employee ID and omits employee search; backend `payroll:list_own` scoping remains authoritative.
- Flutter `PerformanceReviewPage` lists reviews, opens a details dialog, and supports create, edit, and delete. Its service maps the `/performance-reviews/` endpoint. The response schema omitted the review ID, which made update/delete impossible from a list. Search passed an employee ID but the backend had no usable name search. The React slice adds the record ID and display names to the response and server-side search while retaining the existing CRUD endpoints.
- Flutter `WorkReportPage` lists employee daily reports and provides review, submit, edit, and delete entry points. The backend creates personal reports for the signed-in employee and restricts edits/deletes and review decisions by permission, owner, and status. React keeps `/hr/work-report` as an HR register: managers can edit another employee's draft/returned report in a dedicated dialog, delete only eligible other-employee drafts/returned reports, and review submitted reports. Own reports are view-only here and self-review is blocked; employee create/edit remains on `/dashboard/my-reports`.

## API contract and limits

| Route               | Read contract                                                                                                                                                                                                                                              | Mutations and backend rules                                                                                                                                                                                                                                                                                                                                                      |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HR Payroll / My Pay | `GET /api/v1/payroll/`; payroll summaries include employee, period, allowance total, salary totals, status, and disbursement date. The response includes persisted allowance and deduction breakdown maps. My Pay always supplies the current employee ID. | No benefit enrollment or benefit-category CRUD exists. Both pages are read-only; the HR register is cross-employee and My Pay is scoped to the signed-in employee. The deduction breakdown is an additive serializer field over existing JSON model data; no migration or new endpoint is required.                                                                              |
| Performance Reviews | `GET /api/v1/performance-reviews/` with employee/reviewer/date/period/rating filters, pagination, and additive `search`; response includes `id`, employee/reviewer IDs and names, period/date/rating, and review text.                                     | `POST`, `PUT /{id}`, and `DELETE /{id}`. Ratings must be 1–5; a reviewer must differ from the employee; duplicate employee/period rows are rejected.                                                                                                                                                                                                                             |
| HR Work Reports     | `GET /api/v1/work-reports/` with status, content search, date, owner, and pagination filters; details use `GET /{id}`.                                                                                                                                     | HR uses existing update/delete and approve/reject endpoints only; it does not create reports. Managers edit other employees' draft/returned reports and delete only backend-eligible draft/returned reports. Returned edits become drafts and clear review metadata. The server remains authoritative for ownership, branch scope, status transitions, and decision permissions. |

## URL and data lifecycle

| Route query                                                | Query scope and freshness                                                                              | Refresh and invalidation                                                                                                                                                                                                                    |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HR Payroll `search`, `status`, `page`, `pageSize`          | Current user, employee scope, filters, and page; `standard` (60 seconds).                              | Revalidate on stale route entry, focus, and reconnect. No polling or generic refresh action. Payroll rows remain visible during background refresh. No mutation invalidation because the register is read-only.                             |
| My Pay `status`, `page`, `pageSize`                        | Current user and employee ID from the authenticated session, status and page; `standard` (60 seconds). | Always request the signed-in employee ID and do not expose employee search. Backend owner scope remains authoritative. Revalidate on stale route entry, focus, and reconnect; no polling or mutations.                                      |
| Performance Reviews `search`, `rating`, `page`, `pageSize` | Current user, employee scope, filters, and page; `history` (120 seconds).                              | Revalidate on stale route entry, focus, and reconnect. No polling. Create/update/delete invalidate only the performance-review list family; keep rows and drafts visible on mutation failure.                                               |
| HR Work Reports `search`, `status`, `page`, `reportId`     | Current user, employee scope, filters/page, and selected report; `standard` (60 seconds).              | Revalidate on stale route entry, focus, and reconnect. No polling or generic Refresh action. Manager updates/deletes/reviews invalidate HR report lists and the matching detail; there is no HR create path or personal-cache invalidation. |

First-load failures show a local retry; cached rows remain visible after a background refresh error. Filtered-empty results have a clear-filter path. Mutation feedback appears only after server confirmation; failed forms preserve entered values. The Performance Review detail and form dialogs use the shared viewport-clamped dialog, and the work-report detail remains URL-addressable for authorized reviewers.
