# Built Preview QA Audit — 2026-10-20

## Summary

The built React preview loaded successfully against the local development backend. The three dashboards, authentication pages, My Tasks, My Targets, and My Work Reports rendered with data and no page-level alert on the admin account. The full automated suite passed when run serially: **34 test files, 133 tests**.

Three issues need attention before calling the audited experience polished:

1. A valid least-privilege staff account is blocked during session bootstrap because its own role lookup returns `403`.
2. At exactly 1100px, My Targets detail buttons are outside a clipped card and cannot be reached; Work Reports also clips its row action label.
3. At 320px, Attendance readiness rows overflow the narrow content viewport.

There are also two smaller auth presentation issues: the login rejection alert remains stale while credentials are edited, and the direct two-factor route asks for a code before identifying that no verification session exists.

## Follow-up implementation — issues 1–8

Issues 2–8 below were implemented and verified as recorded at the time. The least-privilege bootstrap issue is now addressed in source: `/auth/me` returns the current user's role summary and grants, and React no longer calls the ID-based role endpoint or loads the full permission catalogue during session bootstrap. This latest auth change has not yet been run against the backend, type-checked, or verified with the least-privilege account; the earlier verification record below predates it.

- **2–3, Target and Work Reports clipping:** Both layouts now switch between compact cards and tabular rows based on the list's available container width. This avoids activating a wide table merely because the browser crossed the 1100px sidebar breakpoint. The Work Reports action keeps its full label visible in the table layout.
- **4, Attendance at 320px:** Readiness rows use a constrained grid; status chips move below their descriptions when space is narrow. The two readiness tiles remain stacked until the main content can support two columns.
- **5, Overview heading:** The page retains one H1 (`Overview`); the personalized greeting is an H2.
- **6, Login feedback:** The generic rejection alert clears when either email or password changes. It remains one form alert and preserves the entered draft.
- **7, Two-factor direct route:** Added `GET /api/v1/auth/browser/two-factor/status`, which checks only the HttpOnly pending challenge and returns `{ success, pending }` without token or user identity. The code form appears only for a valid pending challenge. No challenge shows the expired state immediately; a status-check failure offers retry or Login. Expiry during code entry rechecks the status and switches to the expired state.
- **8, local QA report:** Replaced the malformed work text in report 1 for `EMP-TEST-ADMIN` with a deterministic, realistic sample. This was done only in the local DEBUG/SQLite database; no production or other employee records were edited. The existing local staff scenario seed already provides realistic report examples across review states.

Verification after the changes: the full frontend suite passed (**34 files, 136 tests**); all 18 browser-auth backend tests passed; typecheck, lint, formatting, and production build passed. The browser auth endpoint must be present in the backend deployment before a deployed React build can use the 2FA status check; no deployment was performed here.

## Findings

### P1 — Least-privilege staff cannot complete login bootstrap

**Reproduction:** Sign in as `staff2@gmail.com`. Credentials are accepted, but the app leaves the user at the session verification error: “Workspace access could not be verified.”

**Evidence:** Read-only requests using that account returned:

| Request                              | Result |
| ------------------------------------ | ------ |
| `GET /api/v1/auth/me`                | 200    |
| `GET /api/v1/employees/employees/40` | 200    |
| `GET /api/v1/roles/employees/40`     | 403    |
| `GET /api/v1/roles/permissions-map`  | 200    |

The account can read its employee profile and own attendance/work-report resources, but it does not have the broad `roles` view permission required by the role endpoint. The frontend treats that denial as a failed permission bootstrap and blocks access, which is fail-closed but prevents legitimate staff from using the app. The relevant lookup is in [auth.api.ts](../../src/shared/auth/auth.api.ts) and [session.ts](../../src/shared/auth/session.ts).

**Resolution:** The current-user `/auth/me` response now includes a role summary and the permissions granted by that role. React uses those self-scoped grants and no longer depends on `roles.view` or the system permission catalogue to bootstrap. No broad permissions were granted to staff. Runtime verification with `staff2@gmail.com` remains outstanding.

### P2 — My Targets detail actions are clipped at 1100px

At 1100px, the visible target card ends at x=1061, has `overflow: hidden`, and its Details buttons render from x=1120 to x=1209. The controls are completely outside the card and viewport, so users at this breakpoint cannot open target details. This was verified against the built preview. The clipping card is in [my-targets-page.tsx](../../src/modules/targets/routes/my-targets-page.tsx).

### P2 — Work Reports action label is clipped at 1100px

The Work Reports rows fit the viewport, but their final action label spans x=989–1101 while the card ends at x=1076. The rightmost 25px of “View report” are clipped by the card. The full row remains clickable, so this is a visual affordance issue rather than an inaccessible record. The list is in [my-work-reports-page.tsx](../../src/modules/work-reports/routes/my-work-reports-page.tsx).

### P2 — Attendance readiness rows overflow at 320px

After Attendance finishes loading at 320px, the document has a horizontal scroll range and the readiness rows extend beyond the content viewport. Their row boxes end at x=321; the small viewport’s document client width is 305px because the vertical scrollbar occupies space. A horizontal scrollbar appears, and the card edge/status area is cramped. The same route is clean at 375px and above in this sweep. The readiness section is in [attendance-page.tsx](../../src/modules/attendance/routes/attendance-page.tsx).

### P3 — Workspace Overview exposes two top-level headings

The main page has both “Overview” and the personalized “Good morning, Test Admin” greeting as `<h1>` elements. The page content loaded without errors, but two competing H1s weaken the document outline and screen-reader navigation. Keep one page-level H1 and render the greeting at the next appropriate heading level.

### P3 — Login rejection remains after the user edits credentials

Submitting an unknown synthetic address showed one generic form alert and no field errors, as intended. Editing the email left the old “Email or password is incorrect” alert visible; there is no dismiss control. The alert disappears after a successful login. Consider clearing it when the credentials change or adding an accessible dismiss action, so users do not keep seeing a rejection for a previous set of values. The login form is in [login-page.tsx](../../src/modules/auth/routes/login-page.tsx).

### P3 — Direct two-factor URL waits for an unnecessary code submission

Opening `/two-factor-verify` without a pending verification session initially shows the code-entry form. Only after submitting a six-digit code does it show the alert “Your verification session has expired. Please sign in again.” Consider showing the expired state immediately or redirecting to Login when the pending session is absent. The current response is safe and does not authenticate the user.

### Test-data quality issue — Work Report history contains synthetic-looking text

Some existing report descriptions are visibly malformed or placeholder-like, for example “Usuwiwicj Dueuei Jxjdjdjr” and “Kfss95sote95”. This is backend sample data, not a React rendering defect, but it makes the history screen look unfinished and reduces confidence during visual review.

## Authentication and feedback checks

- **Login, empty submit:** Inline Email and Password errors are shown; both fields receive `aria-invalid` and reference the corresponding error IDs. Focus moves to the first invalid field. Correcting a field clears its error after the field interaction/blur.
- **Password visibility:** The Show/Hide password control changes the input type and remains keyboard-accessible as a button.
- **Invalid credentials:** The message is generic, appears once as a form alert, and is not duplicated as a toast. The draft remains editable.
- **Forgot Password:** A synthetic address under `example.invalid` received the neutral “If an account exists…” confirmation only after the request completed. No real user address was used.
- **Reset Password:** A synthetic invalid code produced one form-level alert; it did not mark unrelated password fields invalid. A successful reset was not attempted because no valid reset code was available, and resetting a real test user would invalidate its sessions.
- **Two-factor:** Empty code validation is inline. An invalid code with no pending session produces the explicit expired-session alert. A successful OTP verification was not attempted because no seeded OTP/email delivery path was available.
- **Logout and protected deep link:** Confirmed in the same audit pass: sign-out returns to Login, and a protected URL opened while signed out is preserved as the return target.
- **Profile and two-factor settings:** Profile dialog positioning and the password-confirmation prompt were reviewed previously in this audit sequence. No security setting was toggled.
