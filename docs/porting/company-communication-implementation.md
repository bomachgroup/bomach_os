# Company Broadcast and Approval Workflows

## Scope

- `/company/broadcast` provides Announcements and Events, plus a shortcut to the canonical `/notifications` inbox. Notifications are not duplicated inside Broadcast.
- `/company/approval-workflow` ports workflow configuration and request review in the same route. The dedicated `/company/approval-requests` route remains available for reviewers who need a focused review screen.
- Tabs, search, status filter, and pagination are validated URL state. Only the selected tab's permitted list query runs.
- The pages use shared Bomach layout, cards, controls, dialogs, feedback states, toasts, and TanStack Query lifecycle. There are no page-level refresh buttons or polling loops.

## Permission mapping

- Broadcast route access accepts `announcements:list` or `events:list`. Each tab is hidden unless its own list permission is present. The notification-center shortcut is shown only with `notifications:list`; inbox actions remain on `/notifications`.
- Announcement create/edit/deactivate actions use `announcements:create`, `announcements:update`, and `announcements:delete` respectively. Branch and department audience pickers only list records when `branches:list` and `departments:list` are granted. Specific targets use Branch and Department database IDs from their list endpoints; the department choices endpoint returns string codes and is not valid for the announcement many-to-many `department_ids` contract. If an options request fails, the form shows a retryable error instead of silently treating the missing options as “all.”
- Event create/edit/delete actions use `events:create`, `events:update`, and `events:delete`. The backend additionally restricts event update/delete to its organizer; the React page only offers those actions when the returned `organizer_id` matches the signed-in user.
- Notification list/read actions are implemented on the canonical `/notifications` route and use `notifications:list`, `notifications:mark_read`, and `notifications:mark_all_read` independently.
- Approval Workflows route access accepts either `approval_flows:list` or `approval_requests:list`. Tabs and actions use their own `approval_flows:*` and `approval_requests:*` permissions.

## Known backend limitations

- `required_level` is persisted and displayed as workflow configuration, but the current approve/reject handlers enforce permission and request scope only. They do not compare the acting user's role/level to the current workflow step. This remains a backend limitation; the page avoids repetitive implementation-warning callouts and does not imply role-level enforcement.
- The current Events collection supports search and pagination but no date-range or month filter. The React page presents server-paginated event records rather than a misleading full-month calendar built from only one page of events.
- Event reminder and recurrence response fields are display strings. The editor maps recognized `RRULE` daily/weekly values and reminder minute labels into supported input fields; unknown recurrence formats are treated as non-repeating in the form. No raw event date field or unsupported Flutter event type is sent.
- Event target audiences are backend booleans (all branches/departments/associates/investors/partners); they are not specific branch/department IDs.
- The backend offers no announcement attachment API, announcement delivery destination, or reviewer-level enforcement. No schema migration was required for this page port.

## Data lifecycle and interaction

- Announcement/event/workflow lists use `standard` freshness (60s), search/page-aware user+employee query keys, focus/reconnect revalidation, and `keepPreviousData` pagination. Choice data uses `reference` freshness (300s) and loads on editor open.
- Request list uses the pre-existing `approvalRequestsApi`/query keys so its state is shared with Company Overview and the dedicated Approval Requests route.
- List mutations invalidate only their corresponding list family. Approval decisions also invalidate the Company's approval-request list family and Company Overview. Notification actions remain on `/notifications` and invalidate the existing notification key family.
- Search is submitted explicitly to avoid a request on every keystroke. Filters and page are URL-backed; changed searches/status/tabs reset the page. Empty/error/loading states are distinct and local retries preserve cached data and drafts. Out-of-range pages normalize to the final valid page.
- Dialogs use the shared native-dialog component with labeled controls, responsive scrollable bodies, keyboard dismissal, and fixed action footers. Short record-detail dialogs use the shared content-sized layout. Client-side required/date-order checks focus the invalid control; server errors use the shared error presenter and do not clear drafts.
- Announcement scheduling has an explicit `Publish immediately` switch. When enabled, the publication date/time fields are disabled and the API receives `publish_at: null`; scheduled publication requires a date. Optional expiry has no explanatory helper paragraph. Event and announcement times use the shared styled `TimePickerField` while API values remain local-time inputs serialized to ISO timestamps.
- Event audience selection remains a multi-select of the backend's audience flags. Its trigger reports the selected group count, with the complete selected labels shown as wrapping chips; announcements no longer display the frontend-only permission-aware badge.
- Event cards use the same stacked content/footer arrangement as announcements, with actions right-aligned below event metadata. Audience selection count and chips remain compact. Organizers can edit events only before their start time, matching backend validation; past-start event cards explain that editing has closed. Client validation is shown within the section that needs correction; server save errors remain visible in the open form and preserve the draft.
- Announcement cards keep View, Edit, and Deactivate in a right-aligned footer below the content at every width. Audience summaries stay compact on cards; the detail dialog presents branch and department scope in separate cards with explicit all/targeted state, selected counts, and wrapping target labels. The cards stack in compact dialogs and use two columns at the tablet breakpoint. Full target names remain available in the title/accessible label and detail view.
