# HR Recruitment and Leave Requests

## Scope and source review

- `/hr/job-post` ports the Flutter Recruitment screen: job postings, the applicant pipeline, posting/applicant details, create/edit, and supported status actions.
- `/hr/leave-request` is the HR management register: summary, status/category/search filters, pagination, request details, manager edits to another employee's pending leave/absence request, approvals, rejection feedback, and `request_id` deep links. Employee submission and personal editing remain on the self-service routes.
- The current Flutter Recruitment Pipeline has placeholder pagination and no-op job actions. Its candidate controller calls `/stage` and `/rating` endpoints that do not exist. React uses the backend's supported applicant status enum and status endpoint instead.
- The current backend's job-posting and applicant endpoints did not apply the request's branch scope; this slice adds scoped querysets/object lookup and regression tests. Applicant deletion also called a nonexistent `decrement_applicants()` method; applicant counts are derived from the relation, so the invalid call is removed.

## Backend contract and limits

| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Job postings          | `GET/POST /job-postings/`, `GET/PUT/DELETE /job-postings/{id}`, `PATCH /{id}/status`, `GET /stats/summary`; list/search/status/type/branch/department/active filters; salary min/max; deadline                | `vacancy_count` is returned but not accepted in create/update schemas, so it is read-only/defaulted by the backend. Branch and department are numeric foreign keys; editors use authorized choice endpoints.                                                                                                                                                                                                        |
| Applicants            | `GET/POST /applicants/`, `GET/PUT/DELETE /applicants/{id}`, `PATCH /{id}/status`; list filters by search/job/status                                                                                           | Pipeline columns use `applied`, `shortlisted`, `interviewed`, `offered`, `hired`, `rejected`. No stage or rating API exists. Resume is a URL field; no upload endpoint is provided. LinkedIn/portfolio are accepted on writes but omitted from response schemas, so React does not claim they persist.                                                                                                              |
| Interviews and offers | Per-applicant list/create/update APIs exist with independent `interviews` and `offer_letters` permissions; the endpoints are scoped to the applicant's branch before lookup.                                  | Candidate details expose separately permissioned interview listing/scheduling and offer listing/creation. Offer creation uses the backend's immediate-send flow. Edit/delete are not exposed. Interviewers are selected from the active, scoped employee directory using `employees:list`; interview creation submits the employee record's numeric `id` required by the interviewer foreign key.                   |
| Leave requests        | List filters include search, request ID/kind, leave type/status/date range, and limit/offset; summary is branch/owner scoped. Existing create/update/approve/reject/cancel APIs have dedicated backend rules. | The HR register has no create action. With `leave_requests:update`, HR may edit another employee's pending leave or absence request; running-late requests and own requests are view-only here. Reviewer actions require list plus the corresponding approve/reject permission, active employee status, in-scope branch, pending status, and a different employee from the requester. Rejection reason is required. |

Leave API validation is authoritative: overlapping active leave/absence requests and duplicate active late-arrival reports return `409`; running-late requests use the server's current date and are rejected after clock-in; reviewed requests cannot be reviewed again; only pending requests can be edited/cancelled. React performs early field validation but still presents backend validation/conflict errors without discarding the draft.

## Permissions and durable navigation

- Recruitment entry accepts `job_postings:list` or `applicants:list`. Each tab and action is independently hidden/gated by its own resource/action (`job_postings`, `applicants`, `interviews`, `offer_letters`). API branch scoping remains authoritative.
- Leave Requests entry requires `leave_requests:list`. HR exposes update, approve, and reject only with their exact permissions; it does not expose employee self-service creation. Manager edit is limited to other employees' pending leave/absence requests, while running-late and own requests cannot be edited or decided from HR. Request details use the dedicated `GET /leave-requests/{id}` endpoint and are only opened with `leave_requests:view`; backend object and branch scope remain authoritative.
- Recruitment tab and filters and Leave Requests tab/category/status/search/page are URL-owned and validated. A leave notification link with `request_id` opens the matching request when it is in the signed-in review scope; otherwise the register reports that it is unavailable without leaking record details.

## Data lifecycle

| Query                                   | Key scope and freshness                                                      | Triggers and failure behavior                                                                                                                                                                                                     |
| --------------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Job posting list and summary            | `['hr','recruitment',userId,employeeId,...]`, filters/page; `standard` (60s) | Active route stale entry, focus, reconnect; no polling or generic refresh. Keep rows while fetching; local retry on initial failure; cached rows remain visible with a quiet refresh warning on refresh failure.                  |
| Applicant list                          | Same session scope plus status/search/job/page; `standard` (60s)             | Same triggers and error behavior; only requested route/filter query is active.                                                                                                                                                    |
| Job/applicant detail                    | Session scope plus record ID; `history` (120s)                               | Loaded only when opened; retain detail while refreshing; local initial retry and clear not-found state.                                                                                                                           |
| Branch and department choices           | Session scope and resource; `reference` (300s)                               | Branch/department choices support job filters and editing. Applicant job choices load only when the pipeline or candidate form needs them and the user has job-list permission. Failed choices preserve the form and offer retry. |
| Interview and offer records             | Session scope plus applicant ID; `standard` (60s)                            | Load only in the corresponding candidate detail tab and with the resource's list permission. Create actions invalidate the associated tab and recruitment data.                                                                   |
| Leave request list, summary, and detail | Session scope plus filters/page or request ID; `standard` (60s)              | Active route stale entry, focus, reconnect; no polling. Summary, list, and dedicated detail request have separate retry/error states.                                                                                             |

After successful posting changes, invalidate posting list/summary and matching details; applicant create/update/status/delete also refresh applicant lists/details and posting counts. HR leave updates and decisions set the matching detail and invalidate the manager leave list/summary plus HR overview; the HR page does not create requests or invalidate personal leave caches. Writes show success only after the API confirms them. No unrelated inactive route is eagerly fetched.

## Verification matrix

- API unit tests: query parameters, DTO mapping, date-only serialization, status payloads, and non-2xx errors.
- Page tests: URL filters/deep links, permissions, loading/error/empty/populated states, manager edits to another employee's pending leave/absence, no HR self-submit action, own/running-late/decided request restrictions, form validation and preserved drafts on API failure, successful cache invalidation, disabled duplicate submits, request review/self-review constraints, interview and offer workflows, and all supported candidate/posting statuses.
- Backend tests: branch-limited Recruitment list/detail/create/update/status/delete, rejected cross-branch transfers, leave workflow existing validation and branch-scope tests, and applicant deletion/count behavior.
- Browser QA: routes, forms, dialogs, table/cards, long content, keyboard paths, success/error recovery, and widths 375, 600, 900, 1280, 1600 plus 320px and breakpoint edges. Live mutations only after confirming local development DB and console-only email delivery; use synthetic `QA-<date>-hr-recruitment` / `QA-<date>-hr-leave` records and remove only those fixtures.
